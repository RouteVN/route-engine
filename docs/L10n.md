# L10n

Route Engine implements runtime-selectable, patch-based localization.

## Direction

Localization is patch-based.

- One authored language is the canonical source language.
- The source language lives directly in normal project data.
- Localization packages contain only overrides.
- If an override is missing, the engine shows the original authored value.

This keeps the authoring experience simple:

- authors write the game once in the source language
- translators only provide sparse patches
- missing translations fall back automatically
- there is no duplicated parallel content tree for each language

## Engine Initialization

Route Engine receives complete runtime project data in
`initialState.projectData`. L10n follows the same input model: initialization
may also receive complete, already-loaded L10n data in
`initialState.l10nData`.

```js
engine.init({
  namespace: "my-visual-novel",
  initialState: {
    projectData,
    l10nData: {
      packages: {
        "pkg-a7f3d2": {
          language: "Japanese",
          files: [],
          patches: [],
        },
        "pkg-c9e841": {
          language: "French",
          files: [],
          patches: [],
        },
      },
    },
  },
});
```

The `packages` map keys are L10n IDs and must exactly match their package
directory names under `l10n/`. The package value is the parsed contents of its
`l10n.yaml`.

The initialization rules are:

- `l10nData` is optional. Omitting it runs the canonical source project.
- only packages present in `l10nData.packages` are imported
- no separate import-ID list is needed
- the canonical source language remains in `projectData` and is not repeated
  as an L10n package
- the selected package is device-persisted as
  `global.runtime.localizationPackageId`
- `null` selects the canonical project and is the default when no saved
  preference exists
- a saved package ID is restored when it still names an imported package;
  otherwise initialization safely returns to the canonical project

The host parses the selected YAML files and loads their declared physical
files before calling `engine.init`. Binary file contents are not embedded in
`l10nData`, just as normal project binary assets are not embedded in
`projectData`.

Initialization validates and indexes every imported package before creating
the system store or processing the initial line. The selected package is then
resolved as a read-only overlay over canonical `projectData`; initialization
does not mutate the supplied canonical project.

When `updateProjectData` replaces canonical project data, Route Engine
validates and reapplies the initialized L10n data before installing the new
runtime project.

Each package has one required human-readable `language` value. Package
manifests do not carry format versions, locale codes, source-language
metadata, source revisions, or fallback-package chains. If the selected
package has no patch for a target, the canonical project value is retained.

## Runtime Selection

Every layout template receives the imported options and current selection:

```js
{
  localizationPackages: [
    { l10nId: null, language: null },
    { l10nId: "pkg-a7f3d2", language: "Japanese" },
    { l10nId: "pkg-c9e841", language: "French" },
  ],
  localizationPackageId: null,
}
```

The canonical project is always the first option and uses `l10nId: null`; no
per-option default flag is needed. Its `language` is `null` because canonical
project metadata is not duplicated in an L10n package.

This data follows the same path as `saveSlots`: the internal
`selectLocalizationPackages` selector feeds layout template data. It does not
add a new public RouteEngine method.

An authored language menu can iterate the options and dispatch the normal
system action:

```yaml
"$for package in localizationPackages:":
  - type: text
    content: ${package.language}
    click:
      payload:
        actions:
          updateLocalizationPackage:
            l10nId: ${package.l10nId}
```

`updateLocalizationPackage` accepts an imported string ID or `null` for the
canonical project. It resolves again from canonical project data, updates the
current presentation without replaying gameplay actions, reschedules active
auto mode from the new dialogue length, emits `saveGlobalRuntime`, and renders.

The existing browser persistence flow stores the selection with other
device-local runtime preferences. Hosts hydrate `initialState.global.runtime`
before `engine.init`, as they already do for text speed, volume, and skip
settings.

## Patch Targets

Patches should target stable semantic IDs, not array indexes.

Good targets include:

- `characterId` for character display names
- globally unique `lineId` values for line actions and dialogue content
- `layoutId` + `elementId` for layout text content
- resource IDs for any other authored user-facing text

Avoid:

- array-position based overrides
- generic arbitrary JSON-path patching

## Mutation Semantics

`mode` controls how a patch updates an existing target:

- an omitted `mode` defaults to `replace`
- `mode: replace` replaces the complete target
- `mode: patch` updates only the target fields allowed by that patch type

`operation: add` is separate from update mode and explicitly creates a
language-specific resource. An addition must provide a complete resource
payload and cannot use `mode: patch`.

## Line Patches

Line patches use a globally unique `lineId`. They do not repeat the containing
scene or section IDs.

### Complete Action Replacement

`line.action` replaces the complete selected action payload. It does not
perform a shallow or recursive merge.

```yaml
patches:
  - type: line.action
    lineId: beach-arrival
    actionType: background
    payload:
      resourceId: beach-ja
      transformId: fullscreen
```

The omitted `mode` defaults to `replace`, while `actionType` identifies the
Route Engine action being replaced.

The source line must already contain the selected action. A localization
package cannot use `line.action` to add or remove actions.

System and control-flow actions are not localization targets. This includes
conditions, routing, variable updates, and line-advancement actions.

Choice, form, and other interactive presentation actions may be replaced, but
their protected behavior must remain identical to the source. Validation must
compare IDs, event actions, variable bindings, submit/cancel actions, and other
non-presentational fields before accepting the replacement.

### Dialogue Configuration and Content

Dialogue content is the one field excluded from a complete dialogue-action
replacement. A localized dialogue configuration uses `line.action` with
`ignoreFields: [content]`:

```yaml
patches:
  - type: line.action
    lineId: greeting
    actionType: dialogue
    ignoreFields:
      - content
    payload:
      ui:
        resourceId: japaneseDialogueLayout
      characterId: alice
      persistCharacter: true
```

For a dialogue action:

- `ignoreFields` may contain only `content`.
- `payload` must not also contain `content`.
- every field omitted from `payload`, other than ignored `content`, is removed
  by the replacement.
- the completed action must pass the normal dialogue-action schema.

Dialogue text uses a separate `line.dialogue` patch:

```yaml
patches:
  - type: line.dialogue
    lineId: greeting
    payload:
      content:
        - text: こんにちは
```

`payload.content` must always use the authored dialogue-content array shape.
There is no string shorthand. The complete content array is replaced
atomically; entries are not merged by array position.

When both patch types exist, resolution applies the complete `line.action`
replacement first, preserves the canonical source content, and then applies
the `line.dialogue` content replacement.

### Line Patch Rules

- A package may contain at most one `line.action` for each `lineId` and
  `actionType`.
- A package may contain at most one `line.dialogue` for each `lineId`.
- An omitted `mode` defaults to `replace`.
- `line.action` supports only `mode: replace` and always means complete action
  replacement.
- `line.dialogue` supports only `mode: replace` and always means complete
  dialogue-content replacement.
- No line patch performs generic deep merging.
- Patch payloads must pass the schema for their exact target.

## Resource Item Operations

Resource-item patches use the shared mutation semantics across typed resource
collections:

- an omitted `mode` replaces an existing resource item
- `operation: add` explicitly adds a language-specific resource item

The patch `type` identifies the exact resource schema, such as
`resource.image`, `resource.font`, or `resource.layout`. The target identity is
the resource type plus `resourceId`, so IDs may remain scoped to their resource
collection.

Both addition and replacement use complete item semantics:

- `payload` must pass the normal schema for the selected resource type.
- resource fields are not shallowly or recursively merged.
- `add` requires the ID to be absent from the canonical resource collection.
- replacement requires the ID to exist in the canonical resource collection.
- `operation: add` cannot be combined with `mode: patch`.
- the active fallback chain selects at most one mutation for a resource
  target.
- localized resources are resolved as a read-only overlay and do not mutate
  canonical project data.

An added resource can be referenced by other patches in the same localization
package, including localized line actions and layouts.

## Package Files

Although normal Route Engine project data does not contain a file collection,
a localization package may include additional physical files. Its top-level
`files` field uses the same flat file-entry shape as a RouteVN Creator export:

```yaml
files:
  - fileId: station-sign-ja.png
    mimeType: image/png
```

`fileId` is required and `mimeType` is optional. The package does not contain
the Creator editor's `files.items` map or `files.tree`; those belong to editor
repository state, not the exported package boundary. It also does not repeat
editor-only file metadata such as `type`, `size`, or `sha256`.

Each entry declares a physical file bundled with the localization package.
Resource patches refer to that file through their normal `payload.fileId`
field. `files` remains a top-level array and is empty for a text-only package.

The YAML manifest is not sufficient by itself when `files` is non-empty. The
package must also contain a sibling `files` directory:

```text
l10n/
└── pkg-a7f3d2/
    ├── l10n.yaml
    └── files/
        └── station-sign-ja.png
```

`l10n` is the package collection directory. `pkg-a7f3d2` is an example opaque
L10n ID, not a language value. The directory name must exactly match the L10n ID.
Human-readable language information belongs in `l10n.yaml` and does not
determine the directory name.

Every entry in the YAML `files` array maps to one physical file in that
L10n package's `files` directory. The physical filename is exactly its
`fileId`; the packager must not add, remove, or infer a filename extension.
When a filename has an extension, that extension is part of the `fileId`.
MIME information comes from the optional `mimeType` field.

The `files` directory is flat. A `fileId` used for a packaged file must
therefore be a safe single filename and cannot contain path separators or
directory traversal segments.

The host or packager owns file integrity checks, binary lookup, caching, and
URL resolution. Package validation must reject:

- duplicate `fileId` entries
- a declared `fileId` that conflicts with the canonical project or another
  imported L10n package
- a declared file whose matching physical file is missing
- an undeclared physical file in the package's `files` directory
- references to localized file IDs that are neither in this package's `files`
  nor available from the canonical project

### Image Example

Adding an image introduces a language-specific image resource:

```yaml
patches:
  - type: resource.image
    operation: add
    resourceId: station-sign-ja
    payload:
      fileId: station-sign-ja.png
      fileType: image/png
      width: 1024
      height: 512
```

Replacing an image keeps the canonical logical resource ID but replaces its
entire image-resource definition. Every source reference to that ID resolves
to the localized image:

```yaml
patches:
  - type: resource.image
    resourceId: station-sign
    payload:
      fileId: station-sign-ja.png
      fileType: image/png
      width: 1024
      height: 512
```

Both payloads use the existing `resources.images[resourceId]` shape.

## Implemented Coverage

The runtime currently supports:

- every authored line presentation action through `line.action`
- dialogue content through `line.dialogue`
- player-facing scene names through `story.scene`
- complete add/replace operations for `achievement`, `animation`, `character`,
  `color`, `control`, `font`, `image`, `layout`, `particle`, `sound`,
  `spritesheet`, `textStyle`, `transform`, and `video` resource items
- selected-package and imported fallback resolution
- device-persisted runtime package switching and canonical-project restoration
- selected-package reapplication after `updateProjectData`
- resolver, engine-integration, and exact-schema tests, including every
  supported resource patch type and package-validation failure paths
- paired canonical-source and runtime-switch VT references, including an
  authored click action and package-owned physical image, plus Chromium
  runtime-state verification

Initialization validates localized action and resource payloads with standalone
validators generated directly from the authoritative YAML schemas. Regenerate
them with `bun run generate:l10n-validator` after changing an action or resource
schema; the test suite fails if the generated validators are stale.

Line actions cover line-owned text, presentation, and audio configuration.
Nested voice resources and singleton catalogs are not yet resource patch
targets.

## Scene Names

Scene names are player-facing localization targets. Section names are
authoring/editor metadata and are not localized.

`story.scene` uses an explicit partial patch because a scene contains routing
and authored sections that localization must not replace:

```yaml
patches:
  - type: story.scene
    mode: patch
    sceneId: chapter-one
    payload:
      name: 第一章
```

`story.scene` supports only `mode: patch`; the mode must be explicit and does
not use the default replacement behavior. The referenced `sceneId` must exist.
Its patch schema currently allows only `payload.name`, which must be a string.
Omitted scene fields remain canonical, and the patch cannot change
`initialSectionId`, sections, lines, or other story structure.

## Remaining Design Work

The following areas are not yet settled:

- localization of project title and other host-owned project metadata
- addressing singleton resource catalogs such as `imageGallery`, `musicRoom`,
  and `sceneReplay`
- addressing voices, which are currently nested by scene ID
- protected resource fields that localization replacements must keep identical
  to canonical gameplay data
- dynamic messages, placeholders, plurals, and language-aware value formatting
- right-to-left direction, bidirectional text, localized fonts, and renderer
  contracts
- extraction, source hashes, stale-translation diagnostics, interchange, and
  creator tooling

## Resolution Rule

During initialization, runtime selection, or `updateProjectData`:

1. Read the original authored value.
2. Check the selected L10n package for a patch targeting that exact value.
3. Use the matching patch when present.
4. Otherwise retain the original authored value.

## Template Timing

Localization patches are applied before template interpolation.

That keeps translated strings compatible with existing templating such as
`${variables.*}`.

## Summary

The implemented L10n model is:

- canonical source content in project data
- optional complete L10n package data supplied during engine initialization
- sparse localization patches keyed by stable IDs
- one device-persisted selected package resolved as a read-only overlay
- `null` selection for the canonical project
- layout-facing package options and an authored runtime selection action
- automatic fallback to original authored content
